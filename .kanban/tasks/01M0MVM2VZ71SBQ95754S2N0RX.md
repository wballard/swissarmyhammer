We already drive real `swiftlint` from four `code-hygiene` rules. We use it for function-length, magic-numbers and missing-docs only. SwiftLint decides six more things our prompt rules currently judge, and Airbnb ships three custom regex rules that convert judgment into a deterministic check.

Source: https://raw.githubusercontent.com/airbnb/swift/master/Sources/AirbnbSwiftFormatTool/swiftlint.yml

## Stock rules to turn on

| SwiftLint rule | Supersedes (prompt rule) |
|---|---|
| `implicitly_unwrapped_optional` | `optionals.md` no IUO |
| `force_unwrapping` | `optionals.md` no force unwrap in non-test code |
| `force_try` | `error-handling.md` no `try!` in non-test code |
| `force_cast` | `error-handling.md` no `as!` in non-test code |
| `unused_optional_binding` | `optionals.md` check for nil, do not bind an unused value |
| `unowned_variable_capture` | (new — we have no rule) |
| `legacy_constructor`, `legacy_nsgeometry_functions`, `legacy_cggeometry_functions` | (new — we have no rule) |

Keep our existing test-code carve-outs. `force_unwrapping`, `force_try` and `force_cast` must stay off inside test targets — our rules say "in non-test code" and mean it. Airbnb solves this with `noForceUnwrapInTests` / `noForceTryInTests`, which apply the opposite polarity in tests. Honour the same split.

## The three custom regex rules — copy these

Each one turns an LLM judgment into a regex plus an escape hatch:

1. `no_direct_standard_out_logs` — bans `print`, `debugPrint`, `dump`, `Swift.print`, `_printChanges`, scoped by `match_kinds: [identifier]`. We have NO rule for this.
2. `no_file_literal` — bans `#file`, scoped by `match_kinds: [keyword]`. We have NO rule for this.
3. `no_unchecked_sendable` — bans `@unchecked Sendable`, scoped by `match_kinds: [attribute.builtin, typeidentifier]`.

## The mechanism that matters most

Read Airbnb's `no_unchecked_sendable` message:

> "If you really must use `@unchecked Sendable`, you can add a `// swiftlint:disable:next no_unchecked_sendable` annotation with an explanation for how we know the type is thread-safe…"

The escape hatch IS the documentation. Our `concurrency.md` states the same requirement as pure judgment: "`@unchecked Sendable` requires a documented synchronization invariant. The smell is the *absence* of a lock/isolation mechanism and a comment." A tool cannot judge "is there a documented invariant" — but it CAN require an explicit annotation, and the annotation text is the invariant.

This is the `objectivity-over-judgment` standing order working in production: exemptions become annotations. Write the finding message so it tells the author exactly what to write, as Airbnb's does.
