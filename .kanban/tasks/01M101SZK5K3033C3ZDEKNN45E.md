## What

The `review` engine binds to the repository root of the calling session and
rejects every path outside it. A session cannot review a sibling checkout, even
when that checkout is a live build dependency of the session's own repository.

Reproduction, run in `FoundationModelsRouter`, whose sibling
`FoundationModelsMultitool` is linked into the build by SwiftPM edit mode:

    review file ../FoundationModelsMultitool/Sources/FoundationModelsMultitool/MultiTool.swift

    Error: review pipeline failed: Validator 'scope' error: path
    '../FoundationModelsMultitool/Sources/FoundationModelsMultitool/MultiTool.swift'
    escapes the repository root

An absolute path fails the same way. Setting `cwd`, `root`, `workspace` or
`path` does not move the root.

## Why it matters

Two-repository work is normal here. `FoundationModelsRouter` defines a protocol
and `FoundationModelsMultitool` conforms to it, so one change lands in both and
`swift package edit` links them. The change is one unit of work, but only half
of it can be reviewed from the session that made it.

The present workaround is a second Claude session opened in the sibling
checkout, asked over the cross-session channel to run the review and report the
counts back. That works, and it is what closed tasks `^dmttqz1` and `^f1j3ymz`,
but it needs a human to open the second session and it puts the review result
in a different context from the change.

There is a sharper failure hiding behind this. A cross-repository review has to
be scoped by hand, and a diff scope over a commit that renames a file silently
declines whole rule families while still reporting `findings: 0`. On `^dmttqz1`,
`function-length-swift`, `magic-numbers-swift` and `missing-docs-swift` all
reported "found no file at Sources/FoundationModelsMultitool/MultiTool+Detachment.swift"
because a later commit had renamed it to `MultiTool+Background.swift`. The run
still returned zero findings. That gap was only found because a person read the
declined-rule list.

## What good looks like

A way to review a path outside the calling session's repository root, with the
root stated explicitly rather than inferred. For example an explicit root
argument, or an allowance for sibling directories under a shared parent.

If the restriction is deliberate — and there are good reasons for it — then the
refusal should say so and name the supported alternative, instead of reading as
a path error.

## Acceptance Criteria

- [ ] A session in one repository can review a file in a sibling checkout, or
      the error names the supported alternative.
- [ ] The chosen root is reported in the result, so a reader knows what was
      actually scanned.

## Tests

- [ ] A test drives a review of a path in a sibling directory and asserts the
      documented outcome.
- [ ] A test asserts the error text names the alternative when the path is
      refused.
